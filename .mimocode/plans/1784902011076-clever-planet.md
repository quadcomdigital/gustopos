# Piano: Fix elementi doppi nel database

## Problema identificato

Il database presenta **mancanza di vincoli UNIQUE** su molte tabelle, combinata con pattern **TOCTOU** (Time-of-Check-Time-of-Use) nel repository. Questo permette duplicati sia da race condition concorrenti che da inserimenti multipli.

## Cause principali

### 1. Schema senza vincoli UNIQUE (apps/api/src/db/schema.ts)

**Tabelle critiche senza vincoli:**
- `customers` — nessun UNIQUE su `(tenant_id, phone)` o `(tenant_id, full_name_normalized)`
- `consumerUsers` — nessun UNIQUE su `(tenant_id, email_normalized)` o `(tenant_id, phone_normalized)`
- `loyaltyPoints` — nessun UNIQUE su `(tenant_id, customer_id)`
- `fiscalClosures` — nessun UNIQUE su `(tenant_id, business_date)`
- `menuItems` — nessun UNIQUE su `(tenant_id, name)`
- `categories` — nessun UNIQUE su `(tenant_id, name, scope)`
- `staff` — nessun UNIQUE su `(tenant_id, pin)` (rischio sicurezza)
- `tenants` — nessun UNIQUE su `slug` e `subdomain`
- `tenantModules` — nessun UNIQUE su `(tenant_id, module_key)`
- `roles` — nessun UNIQUE su `(tenant_id, key)`

**Nota:** La migration 0009 aveva aggiunto `UNIQUE INDEX` su `customers.phone`, ma la migration 0029 (multitenancy) ha ricreato la tabella senza preservare il vincolo. Stessa cosa per `consumerUsers` (migration 0024).

### 2. Pattern TOCTOU nel repository (apps/api/src/repository/app.repository.ts)

Le funzioni controllano l'esistenza prima di inserire, ma senza vincoli DB il check non protegge da race condition:

- **Linea 6887-6914: `createOrReuseCustomer()`** — check phone/name poi insert
- **Linea 3990-4037: `createConsumerUser()`** — check email/phone poi insert
- **Linea 9241-9289: `earnLoyaltyPoints()`** — check poi insert/update
- **Linea 9041-9073: `createFiscalClosure()`** — check data poi insert
- **Linea 8875-8937: `clockIn()`** — check open entry poi insert

### 3. Query JOIN senza DISTINCT

- **Linea 2963-2989: `listInventoryItems()`** — JOIN su `supplierIngredients` senza DISTINCT
- **Linea 10439-10460: `getReorderSuggestions()`** — stesso problema
- **Linea 8315-8328: `listSupplierIngredients()`** — nessun DISTINCT
- **Linea 8422-8438: `getSupplierIngredientsForPo()`** — nessun DISTINCT

## Piano di intervento

### Step 1: Aggiungere vincoli UNIQUE allo schema

File: `apps/api/src/db/schema.ts`

Aggiungere `uniqueIndex()` alle seguenti tabelle:

```typescript
// customers (linea ~425)
uniqueIndex("customers_tenant_phone_idx").on(table.tenantId, table.phone),
uniqueIndex("customers_tenant_name_idx").on(table.tenantId, table.fullNameNormalized),

// consumerUsers (linea ~291)
uniqueIndex("consumer_users_tenant_email_idx").on(table.tenantId, table.emailNormalized),
uniqueIndex("consumer_users_tenant_phone_idx").on(table.tenantId, table.phoneNormalized),

// loyaltyPoints (linea ~801)
uniqueIndex("loyalty_points_tenant_customer_idx").on(table.tenantId, table.customerId),

// fiscalClosures (linea ~609)
uniqueIndex("fiscal_closures_tenant_date_idx").on(table.tenantId, table.businessDate),

// menuItems (linea ~64)
uniqueIndex("menu_items_tenant_name_idx").on(table.tenantId, table.name),

// categories (linea ~447)
uniqueIndex("categories_tenant_name_scope_idx").on(table.tenantId, table.name, table.scope),

// staff (linea ~15)
uniqueIndex("staff_tenant_pin_idx").on(table.tenantId, table.pin),

// tenants (linea ~722)
uniqueIndex("tenants_slug_idx").on(table.slug),
uniqueIndex("tenants_subdomain_idx").on(table.subdomain),

// tenantModules (linea ~734)
uniqueIndex("tenant_modules_tenant_key_idx").on(table.tenantId, table.moduleKey),

// roles (linea ~751)
uniqueIndex("roles_tenant_key_idx").on(table.tenantId, table.key),
```

### Step 2: Generare ed eseguire la migration

**Nota:** Prima di migrare, verificare che non ci siano già duplicati nel database. Se ci sono, la migration fallirà e bisognerà prima pulire i dati.

### Step 3: Sostituire pattern TOCTOU con upsert

File: `apps/api/src/repository/app.repository.ts`

Sostituire i pattern check-then-insert con `INSERT ... ON CONFLICT`:

**`createOrReuseCustomer()` (linea 6887):**
```typescript
const [result] = await db.insert(customers).values({
  id, tenantId, phone: parsed.phone, fullNameNormalized: normalized, ...
}).onConflictDoUpdate({
  target: customers.phone,
  set: { fullNameNormalized: normalized, updatedAt: new Date() }
}).returning();
```

**`earnLoyaltyPoints()` (linea 9241):**
```typescript
const [result] = await db.insert(loyaltyPoints).values({
  id, tenantId, customerId, points: 0, ...
}).onConflictDoUpdate({
  target: [loyaltyPoints.tenantId, loyaltyPoints.customerId],
  set: { points: sql`${loyaltyPoints.points} + ${pointsEarned}` }
}).returning();
```

**`createFiscalClosure()` (linea 9041):**
```typescript
const [result] = await db.insert(fiscalClosures).values({
  id, tenantId, businessDate: parsed.businessDate, ...
}).onConflictDoNothing().returning();
if (!result) throw new Error("Fiscal day already closed");
```

### Step 4: Aggiungere DISTINCT alle query JOIN

File: `apps/api/src/repository/app.repository.ts`

**`listInventoryItems()` (linea 2963):**
```typescript
const rows = await db.selectDistinct().from(inventory)
  .leftJoin(...)
  .where(eq(inventory.tenantId, tenantId));
```

Applicare lo stesso pattern a:
- `getReorderSuggestions()` (linea 10439)
- `listSupplierIngredients()` (linea 8315)
- `getSupplierIngredientsForPo()` (linea 8422)

### Step 5: Verifica e pulizia dati esistenti

Prima della migration, verificare duplicati esistenti:

```sql
-- Controllare duplicati per ogni tabella critica
SELECT tenant_id, phone, COUNT(*) FROM customers WHERE phone IS NOT NULL GROUP BY tenant_id, phone HAVING COUNT(*) > 1;
SELECT tenant_id, email_normalized, COUNT(*) FROM consumer_users WHERE email_normalized IS NOT NULL GROUP BY tenant_id, email_normalized HAVING COUNT(*) > 1;
SELECT tenant_id, customer_id, COUNT(*) FROM loyalty_points GROUP BY tenant_id, customer_id HAVING COUNT(*) > 1;
SELECT tenant_id, business_date, COUNT(*) FROM fiscal_closures GROUP BY tenant_id, business_date HAVING COUNT(*) > 1;
```

Se ci sono duplicati, creare uno script di pulizia che:
1. Identifica i record duplicati
2. Mantiene il più recente (o quello con più dati associati)
3. Elimina gli altri, aggiornando eventuali foreign key
