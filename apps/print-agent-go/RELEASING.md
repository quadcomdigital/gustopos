# Print Agent — Versioning & Release Process

This document describes how to version, build, and publish the GustoPOS Print
Agent (Go) so that a new release is reproducible and the public download page
stays in sync with the binaries.

## Where things live

| Path | Purpose |
|---|---|
| `apps/print-agent-go/` | Go source (`agent.go`, `api.go`, `config.go`, `main.go`, `pairing.go`, `qz.go`) |
| `apps/print-agent-go/bin/` | Release binaries (git-ignored, generated by `make`) |
| `apps/print-agent-go/scripts/publish-downloads.sh` | Generates the download page + metadata |
| `apps/web/public/downloads/` | **Published artifacts** (git-ignored) served at `/downloads/` |

## Versioning scheme

We use **SemVer** (`MAJOR.MINOR.PATCH`). Until 1.0, treat every change as
backward-incompatible for protocol reasons unless explicitly stated.

The single source of truth for the version is the `VERSION` variable in the
**Makefile** (default `0.7.0`). It is injected into the binary at link time
via `-X main.version=$(VERSION)` and into the download page / `version.json`
by the publish script.

When you change the version, change it **only** in the Makefile:

```make
VERSION ?= 0.7.0
```

> Do not hardcode the version in Go source. The `version` var in `main.go`
> is meant to be overwritten by the linker flag.

### Version bump rules

- **PATCH** (`0.7.0` → `0.7.1`): bug fixes, no API/protocol contract change.
- **MINOR** (`0.7.0` → `0.8.0`): new features, additive changes.
- **MAJOR** (`0.x` → `1.0.0`): breaking protocol/API changes, or when the
  agent is declared production-ready.

When a change affects the **QZ Tray wire protocol** (`qz.go`), the pairing
flow (`pairing.go`), or the **API contracts** (`api.go`), it must ship with
at least a MINOR bump so the version.json `generatedAt` + checksum trail is
clear for support.

## Releasing a new version (step by step)

```bash
cd apps/print-agent-go

# 1. Bump the version in the Makefile (VERSION ?= x.y.z)

# 2. Build the release binaries for all platforms
make linux windows darwin

# 3. Sanity check the build (version string must print the new version)
./bin/gustopos-print-agent-linux-amd64 -version
go vet ./...

# 4. Publish to the web app's public folder
make publish-downloads          # uses VERSION from the Makefile
#    or, to override on the CLI:
make publish-downloads VERSION=0.7.0
```

`make publish-downloads` runs `scripts/publish-downloads.sh` which:

1. Copies every `bin/gustopos-print-agent-*` artifact into
   `apps/web/public/downloads/bin/`.
2. Regenerates `apps/web/public/downloads/checksums.sha256`
   (one `sha256sum` line per artifact, paths relative to `/downloads/`).
3. Regenerates `apps/web/public/downloads/version.json` containing the
   app name, version, `generatedAt` timestamp, and the full artifact list
   (file name, sha256, size in bytes).
4. Regenerates `apps/web/public/downloads/index.html` — the public page
   (in Italian) with OS-categorized download cards, install instructions,
   and integrity-check instructions.

### 5. Publish the web build

The `downloads/` folder lives under `apps/web/public/`, so it is copied into
the API-served `dist/` only when the web app is built:

```bash
npm run build --workspace @gustopos/web   # or: npm run build
```

Then deploy (PM2): `pm2 restart ecosystem.config.cjs` (or whatever your
deploy flow is) so the API serves the new `/downloads/` page.

## Verifying a release

- `curl -s <origin>/downloads/version.json` → `"version"` must equal the
  Makefile `VERSION`.
- Download each artifact **plus `checksums.sha256`** into the same folder and
  verify from there: `sha256sum -c checksums.sha256` (the manifest stores
  relative paths, so the command must run in the folder where you saved both).
- Confirm the linux binary reports the version:
  `./gustopos-print-agent-linux-amd64 -version`.

## Rollback

If a release is broken:

1. Rebuild the previous version (`git checkout` the tag/commit with the
   previous `VERSION`, or set `VERSION` back).
2. Run `make linux windows darwin && make publish-downloads`.
3. Rebuild + redeploy the web app (the download page and checksums are
   regenerated from the binaries, so they are always consistent).

Binaries are static (`CGO_ENABLED=0`, `-trimpath`, `-ldflags "-s -w"`), so
they run on the target OS without extra runtime dependencies.

## Updating the download page content

The page copy (Italian) lives inline in `scripts/publish-downloads.sh`
(the `index.html` heredoc). Edit it there, then re-run
`make publish-downloads` — never hand-edit the generated
`apps/web/public/downloads/index.html`.

## macOS / Windows caveats

- macOS binaries are **not notarized**: first launch on a Mac shows a
  Gatekeeper warning ("Open Anyway" in System Settings → Privacy & Security).
- Windows binaries are **not code-signed**: SmartScreen may warn. This is
  expected for self-distributed binaries; document it in your support flow.

## Checklist before shipping

- [ ] `VERSION` bumped in the Makefile
- [ ] `make linux windows darwin` clean (`go vet` + gofmt too)
- [ ] `./bin/gustopos-print-agent-linux-amd64 -version` prints the new version
- [ ] `make publish-downloads` regenerated all three files (`index.html`,
      `checksums.sha256`, `version.json`)
- [ ] `sha256sum -c checksums.sha256` passes (run in the downloads folder)
- [ ] Web app rebuilt and deployed; `/downloads/` reachable on the public origin
